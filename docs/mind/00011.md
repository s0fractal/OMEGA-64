# Phase 18: Σ-CORE The Pulse Orchestrator (Single-Threaded Baseline)

## Контекст (Context)

Всі мікро-механіки (ALU, Фізика, Структури, Метаболізм) реалізовано та покрито
юніт-тестами. Тепер нам потрібен "Диригент", який буде викликати їх у
правильному порядку, імітуючи `PULSE_WORKER.ts` та `PULSE.ts` з Deno-еталону. Ця
фаза створить послідовний (single-threaded) цикл пульсу, який стане нашим
еталоном для перевірки детермінізму перед розпаралелюванням.

## Крок 1: Оркестратор Пульсу (`src/pulse.rs`)

Створи структуру `PulseOrchestrator`. Реалізуй метод
`pub fn tick(&mut self, state: &mut SigmaState, tick_number: u32)`. Порядок
викликів у цьому методі МАЄ бути ідентичним до Deno-еталону (`PULSE.ts` ->
`tick()`):

1. **`build_spatial_hash`**: Очищення та розкидання атомів по комірках.
2. **`sync_read_views` (Double Buffering)**: На початку тіку скопіюй поточні
   значення `xs`, `ys`, `energies`, `resonances` у відповідні буфери для читання
   (`read_xs`, `read_ys` тощо). Це гарантує, що під час виконання атомів
   (крок 3) порядок обробки не вплине на результат (всі читають стан на початок
   тіку).
3. **Execution Phase (`execute_atom`)**: Цикл від `0` до `MAX_ATOMS`. Для
   кожного живого атома (`ids[i] != 0`) виклич `vm.step(state, i)`.
   - _Важливо:_ Якщо атом генерує `sys_calls` або `intents` (наприклад, рух або
     зміна енергії), застосовуй їх одразу до робочих (write) буферів, АЛЕ
     пам'ятай, що інші атоми в цьому тіку повинні бачити старі координати через
     `read_views`.
4. **Resolution Phase**:
   - `resolve_bond_requests()`
   - `drain_spawn_requests(tick_number)`
5. **Environment Phase**:
   - `tick_glyph_transport(tick_number)`
   - `tick_structure_grid()`
6. **Metabolism Phase**:
   - `apply_metabolism_kernel(...)` — списування базових податків і застосування
     констант гомеостазу (зараз можна захардкодити дефолтні значення з
     `RUNTIME_POLICY`).
7. **Immune Phase (Збирання сміття)**:
   - Пройдися по всіх атомах. Якщо `energies[i] <= 0`, виклич `recycle_atom(i)`
     (очистити `ids`, `bonds`, `logic` тощо).

## Крок 2: Інтеграційний тест детермінізму (Free Run Parity)

Ми маємо довести, що наш монолітний цикл працює так само, як у Deno на довгій
дистанції. Додай тест `test_gt02_free_run_no_ingress` у
`tests/golden_traces_test.rs`.

1. Ініціалізуй порожній `SigmaState`.
2. Засій 5-10 атомів з геномом "Виробника" (`producerLogic` з
   `run_ecosystem.ts`) та 2-3 "Хижака" (`SIMPLE_PREDATOR_SCRIPT`).
3. Виклич `orchestrator.tick(state, t)` у циклі 100 разів.
4. Після 100 тіків зніми `hash` з `energies` та `ids` масивів.
5. **Увага:** Цей тест поки що не зможе ідеально зійтися з Deno, бо в Deno
   працюють багатопотокові гонки. Твоя мета на цьому кроці — зробити так, щоб
   тест проходив декілька разів поспіль у Rust і видавав _стабільний_, 100%
   ідентичний результат від запуску до запуску (Self-Determinism).

## Правила (Constraints)

- Слідкуй за позичаннями (Borrowing). `vm.step` модифікує стан, тому в Rust тобі
  доведеться акуратно обходити правила Mutability. Використовуй внутрішні методи
  `SigmaState` або тимчасові масиви `intents`, якщо Borrow Checker сваритиметься
  на одночасний доступ.
- Не використовуй `unsafe` для обходу borrow checker-а у фазі виконання! Дизайн
  має бути safe-first.
